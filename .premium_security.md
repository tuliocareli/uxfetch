# UX Fetch Premium - Diretrizes e Regras de Segurança (CONFIDENCIAL)

Este documento centraliza as diretrizes de segurança estritas que o agente de IA e a equipe de desenvolvimento devem seguir ao construir a aplicação **UX Fetch Premium** (`uxfetch-pro`).

## 1. Gestão de Chaves e Variáveis de Ambiente
- **Regra de Ouro:** Nenhuma chave (`SUPABASE_URL`, `SUPABASE_KEY`, `STRIPE_SECRET_KEY`, `RESEND_API_KEY`) deve ser "hardcoded" (escrita diretamente no código) sob nenhuma circunstância.
- **Isolamento:** Variáveis sensíveis do backend (ex: chaves de pagamento, Supabase Service Role) **NUNCA** devem ser expostas ao frontend. Em frameworks como Next.js, garanta que elas **NÃO** possuam o prefixo `NEXT_PUBLIC_`.
- **Commits:** Antes de qualquer commit, verifique se o `.env` ou qualquer log contendo tokens está no `.gitignore`.

## 2. Supabase e Banco de Dados (Row Level Security - RLS)
Como o Open Source e o Premium dividem o mesmo banco de dados, a segurança das tabelas (RLS) é a linha de defesa mais crítica.
- **Isolamento de Usuários:** Ao criar tabelas privadas (ex: `user_saved_jobs`, `user_payments`), o RLS deve ser **obrigatoriamente habilitado**.
- **Políticas Estritas:** A política de `SELECT`, `INSERT`, `UPDATE` e `DELETE` deve sempre conter a condição `auth.uid() = user_id`. Um usuário logado não pode, de maneira alguma, ler, modificar ou deletar registros (vagas salvas, dados de pagamento) de outro usuário.
- **Views (Visões):** Views criadas no Supabase (como métricas) que agregam dados devem ser criadas com a flag `WITH (security_invoker = true)` para não expor os dados pela API pública.
- **Roles:** O Frontend só deve acessar o Supabase usando a chave `anon` (anônima), e as lógicas privilegiadas (ex: confirmar que um pagamento foi realizado para ativar o plano Pro) devem ser feitas via Edge Functions, Webhooks ou Servidor Backend usando a `service_role_key`.

## 3. Autenticação e Autorização (Supabase Auth)
- Todo endpoint do backend ou Edge Function privada deve obrigatoriamente extrair o JWT do cabeçalho `Authorization` e verificar se o usuário é autêntico através da API do Supabase Auth. Não confie apenas no payload vindo do cliente.
- Ao fazer o "Snapshot" de uma vaga (salvar no Kanban), valide o token de sessão do usuário primeiro. Nenhuma vaga deve ser atrelada sem um JWT válido.

## 4. Pagamentos e Webhooks (Stripe / Mercado Pago)
- O status de `is_pro` (plano pago ativo) **NUNCA** deve ser alterado confiando em requisições feitas pelo frontend.
- A única entidade autorizada a promover um usuário para o plano Pro é o **Webhook de Pagamento** vindo diretamente da Stripe/MercadoPago para o seu servidor.
- Todo Webhook de pagamento deve **validar a assinatura secreta (Signature)** do cabeçalho da requisição para garantir que foi realmente a plataforma de pagamento que enviou o evento, evitando fraudes (Spoofing).

## 5. Proteção de Frontend e Anti-Spam
- Validações de formulários devem ocorrer tanto no frontend (UX) quanto no backend (Segurança). 
- Utilize proteção contra CSRF em requisições de estado se aplicável, e mantenha o Turnstile (Cloudflare) ativo nas rotas públicas abertas.
- As "Magic URLs" de integração entre o e-mail gratuito e o Kanban pago (ex: clicar no e-mail para salvar a vaga direto no painel) devem ser protegidas. Se a rota envolver estado, deve requerer login prévio.
